# AlphaHive 候选决策交互与前端融合升级方案

日期：2026-07-10  
范围：AlphaHive V3 候选审查、人工决策、现有前端融合  
结论性质：产品与技术方案，不涉及真实交易

## 1. 结论先行

当前“集中列出多个币种，再让 Owner 逐个判断”的方式不是最终形态，而是 V3 第一阶段为了快速获得人工决策样本而搭建的研究型交互。

证据很明确：

- V3 规范要求每次扫描产生 10–20 个候选，只把 Top 5 送入人工审查，其余自动跳过。
- 当前决策输入是 Markdown 报告，结果写入 CSV 台账，再由脚本批量回写。
- 现有前端已经能展示因子、回测曲线和研究指标，但尚未接入 V3 候选队列，也没有候选详情、决策按钮或审计回写能力。
- V3 的冻结快照已经包含 90 天 OHLCV、资金费率、OI、成交额和 BTC 基准，足以在系统内生成大部分决策所需信息；用户不应再手动去平台逐币搜索基础行情。

推荐目标是：**聊天只负责提醒和摘要，前端负责完整审查与决策，台账负责审计，真实交易继续保持隔离。**

## 2. 当前系统现状

### 2.1 当前候选决策链路

```text
异常扫描
  → 每次产生 10–20 个候选
  → Top 5 进入人工审查
  → 自动生成 Markdown 长表/候选清单
  → Owner 在聊天中逐个判断
  → 脚本回写 Anomaly_Ledger.csv
  → 重新计算 4h/24h/72h/7d 结果和研究闸
```

这条链路的数据闭环已经存在，但人机交互仍停留在“报告驱动”，缺少产品化的决策界面。

### 2.2 已有前端资产

| 前端 | 当前用途 | 可复用部分 | 不适合直接复用的部分 |
|---|---|---|---|
| `alpha_hive/dashboard` + `alpha_hive/server/app.py` | 因子研究与回测展示 | 浅色视觉体系、左侧列表、指标卡、Plotly 图表、FastAPI 接口、静态降级模式 | 当前只认识 factor/receipt/curve，没有候选和写入接口 |
| `alpha_hive/system/templates/dashboard.html` | Agent 状态、任务队列、Token、关键发现 | 任务状态、后台运营概览 | 更像运维后台，信息层级不适合逐个做市场判断；依赖另一套 Flask 服务 |
| `AlphaHive_V3` | 候选、冻结快照、基线、决策台账、回放结果 | 候选审查所需的主要数据和审计基础 | 没有前端和服务层，CSV 不能直接安全地承接多人/多标签页写入 |

### 2.3 当前交互的主要问题

1. **认知负担过高**：一次出现 6–20 个币，用户必须记住每个币的上下文并在外部平台反复搜索。
2. **信息不是“决策包”**：报告给出触发数值，但缺少同屏 K 线、BTC 对照、资金费率/OI 变化、重复出现历史和数据质量提示。
3. **优先级不足**：强候选、普通 Watch、数据异常币混在一个长表中，Owner 的注意力没有被保护。
4. **同币重复审查**：例如 LAB 在不同扫描时点重复出现，当前按记录逐行展示，没有按币种聚合历史。
5. **动作成本高**：决定、方向、理由和假设没有结构化表单，聊天回复还需要二次解析和回写。
6. **研究泄漏风险**：历史回放已经有事后收益。若决策页不严格以 `scan_time_utc` 截断，就可能把未来数据带入人工判断。
7. **前端割裂**：因子研究、Agent 运营、V3 候选分属三处，没有统一导航和状态模型。

## 3. 目标交互：从“币种清单”变为“决策收件箱”

### 3.1 用户收到的消息

聊天/飞书/Telegram 不再发送完整币种长表，只发一条摘要：

```text
本轮发现 12 个异常候选：
- 2 个需要你决策（1 个高优先级）
- 4 个进入观察
- 6 个因质量/门槛自动过滤

最高优先：SUIUSDT
原因：三重触发，99.9% 分位，24h 成交额 $1.8B

[打开候选审查台]
```

原则：通知里最多展开 1–3 个最高优先项，完整列表留在前端。

### 3.2 前端审查主流程

```text
候选收件箱
  → 系统自动去重、分级、标注风险
  → Owner 打开一个候选详情
  → 同屏完成行情/信号/质量/上下文检查
  → 选择 No Trade / Watch / Paper Trade
  → 若为 Paper Trade，再明确 Long / Short、假设、失效条件和观察周期
  → 保存并自动切到下一个候选
  → 全部完成后生成本轮摘要并触发后续研究计算
```

### 3.3 页面信息架构

建议在现有浅色 R1 前端增加顶层导航：

```text
总览 | 候选审查 | Paper 观察 | 因子研究 | 系统状态
```

“候选审查”采用三栏布局：

| 区域 | 内容 |
|---|---|
| 左栏：审查队列 | 待决策数量、优先级、币种、触发时间、推荐动作、数据质量标记；支持 Pending/Watch/Done 筛选 |
| 中栏：决策证据 | 24h/7d/90d K 线、成交量、相对 BTC 表现、资金费率、OI、触发点、同币历史出现时间线 |
| 右栏：决策面板 | 系统建议及置信度、支持证据、反对证据、缺失信息、No Trade/Watch/Paper Trade、方向、假设、失效条件、备注 |

移动端或窄屏改为“队列 → 详情 → 决策”的单列步骤，不强行保持三栏。

## 4. 单个候选应提供的“决策包”

用户无需离开系统就能看到：

### 4.1 已经具备的数据

- 币种、扫描时间、排名、历史覆盖等级、是否允许 Paper。
- 触发原因、触发分位、24h 绝对涨跌、相对 BTC 超额涨跌。
- 24h 成交额、资金费率方向与数值、OI（有数据时）。
- 冻结快照中的 90 天 1h OHLCV。
- 同扫描时点 BTC 基准。
- 红队建议、置信度、人工检查项、否决标记。
- 同币种在其他扫描/回放中的出现记录。

### 4.2 前端应现场计算的视图

- 以扫描时点为终点的 24h/7d/30d/90d K 线。
- 币种与 BTC 的归一化相对强弱曲线。
- 24h 成交额相对过去 30/90 天的位置。
- 资金费率和 OI 的趋势，而不是只显示最后一个数值。
- 当前触发在历史分布中的位置。
- 数据质量卡：缺失率、异常跳点、合约映射风险、快照是否完整。

### 4.3 可以保留的外部链接

- “在交易所查看”和“在图表平台查看”作为二次核验快捷入口。
- 外链不是完成基础审查的前提。
- 对历史回放记录，外链只用于查事件背景，决策证据仍以冻结快照为准。

### 4.4 尚缺的数据

- 订单簿深度和真实点差。
- 交易所合约状态、上线/迁移/维护事件。
- 结构化新闻与项目事件上下文。
- 跨交易所成交量一致性。

这些内容应在第二阶段作为增强项接入。第一阶段要明确显示“未提供”，不能用估算值伪装成已验证事实。

## 5. 自动分流规则

目标不是让系统替 Owner 交易，而是减少低价值人工检查。

### 5.1 系统可自动完成

- 把非 Top 候选保持为 `AutoSkipped`。
- 将相同币种、相近时间、相同触发的记录合并成一个审查组。
- 对明显数据异常标记为“质量阻断”，默认建议 No Trade。
- 按流动性、触发强度、数据完整度和红队置信度排序。
- 自动生成支持证据、反对证据和缺失信息摘要。
- 对 Watch/No Trade 提供“一键接受建议”，但仍记录操作人和时间。

### 5.2 必须由 Owner 明确完成

- Paper Trade 的最终批准。
- Long/Short 方向。
- 可检验假设、失效条件和观察周期。
- 对质量阻断的强制覆盖。

### 5.3 不应出现在这个页面的动作

- 真实下单。
- API Key 管理。
- 杠杆、仓位和资金划转。

候选审查台保持 Research/Paper 边界，避免“研究确认按钮”被误解为真实交易按钮。

## 6. 最重要的研究安全约束

### 6.1 决策态与评估态必须物理分开

同一候选分成两个标签：

- **决策证据**：只允许读取 `timestamp <= scan_time_utc` 的数据。
- **事后评估**：只有提交决定后才显示 4h/24h/72h/7d 结果。

后端必须做时间截断，不能只靠前端隐藏未来数据。

### 6.2 所有修改必须可追溯

每次操作追加记录：

- operator
- timestamp_utc
- record_id
- old decision/direction
- new decision/direction
- hypothesis/invalidation/horizon
- reason
- data_snapshot_id
- client_request_id

现有 `manual_override_log.csv` 可以先承接追加审计，但不建议继续由前端直接改主 CSV。

### 6.3 写入需要一致性保护

- 决策接口校验当前版本，防止两个页面互相覆盖。
- 每次提交使用唯一请求 ID，避免重复点击产生双写。
- Paper Trade 必须满足方向和假设等跨字段规则后才能保存。
- 强制覆盖必须二次确认并写入 override log。

## 7. 推荐技术融合方式

### 7.1 推荐主线

以 `alpha_hive/server/app.py` 的 FastAPI 和 `alpha_hive/dashboard` 的浅色 R1 前端作为统一入口，新增 V3 Review 模块。

理由：

- 已经有前后端连接、静态降级和 Plotly 图表能力。
- R1 的“左侧列表 + 主视图 + 指标卡”与候选审查天然接近。
- 可逐步加入页面，不需要先重写整个前端。
- 可以把旧 Agent 看板作为“系统状态”页面后续迁入，而不是维护 Flask/FastAPI 两套长期服务。

### 7.2 不推荐的方式

- 不建议在 `AlphaHive_V3` 下再新建第三套独立前端。
- 不建议让浏览器直接读取和修改 CSV。
- 不建议先上 React/Vue 大重构；当前 Vanilla JS + Plotly 足够完成 MVP，先验证决策流程，再决定是否组件化迁移。

### 7.3 建议新增的后端模块

```text
alpha_hive/server/
  app.py
  v3_review_service.py       # 读队列、构建决策包、校验决定
  v3_review_repository.py    # 受控读写 ledger / audit log
  v3_review_models.py        # API 字段和跨字段验证
```

V3 根目录通过配置传入，例如 `ALPHAHIVE_V3_ROOT`，不要把绝对路径散落在接口代码中。

### 7.4 建议接口

| 接口 | 用途 |
|---|---|
| `GET /api/v3/review/summary` | 本轮待审、质量阻断、Watch、已完成数量 |
| `GET /api/v3/review/queue` | 按状态、优先级、run、symbol 获取队列 |
| `GET /api/v3/review/candidates/{record_id}` | 返回以扫描时点截断的完整决策包 |
| `POST /api/v3/review/candidates/{record_id}/decision` | 提交结构化决定并写审计 |
| `GET /api/v3/review/candidates/{record_id}/evaluation` | 决策后读取事后结果 |
| `GET /api/v3/review/symbols/{symbol}/history` | 相同币种的跨 run 历史 |

## 8. 分阶段实施方案

### Phase A：只读候选审查台

目标：先消除“逐币去平台搜索”的痛点，不改写任何决策数据。

- 新增统一导航和“候选审查”页面。
- 读取 V3 台账、run manifest 和冻结快照。
- 展示队列、完整决策包、K 线、BTC 对照、funding/OI、历史重复记录。
- 严格实现 scan time 截断。
- 提供交易所/图表平台核验链接。
- 显示缺失信息和数据质量风险。

验收：用户可以在不打开外部平台的情况下完成至少 80% 的基础判断。

### Phase B：结构化决策与审计回写

目标：把聊天回复和脚本批量解析替换为前端可审计表单。

- 增加 No Trade / Watch / Paper Trade 表单。
- Paper Trade 强制方向、假设、失效条件和周期。
- 写入服务、版本校验、幂等保护、追加审计。
- 提交后自动进入下一条，支持草稿保存。
- 全部完成后生成摘要并触发后续研究计算。

验收：100% 决策带操作人、时间、证据快照和审计记录；没有直接 CSV 双写。

### Phase C：智能分流与信息增强

目标：让 Owner 只处理真正需要判断的少量候选。

- 相同币种/相近扫描合并。
- 数据异常自动阻断。
- 结构化新闻、交易所状态、跨交易所成交验证。
- 订单簿深度和点差接入。
- Chat/飞书/Telegram 只推送摘要和深链接。

验收：单次通知展开不超过 3 个候选；人工逐条审查量相对原流程下降 50% 以上。

### Phase D：统一 AlphaHive 工作台

目标：结束多套前端并存。

- 把旧 Agent 看板的系统状态、任务和关键发现迁入统一入口。
- 保留“候选审查”“Paper 观察”“因子研究”“系统状态”四个业务区。
- 统一启动方式、配置、样式、错误提示和权限边界。

## 9. MVP 页面验收清单

- [ ] 首屏明确显示“待你决定”的数量，而不是直接铺满币种。
- [ ] 默认只选中最高优先级的一个候选。
- [ ] 同屏显示 K 线、BTC 对照、成交量、资金费率、OI 和触发解释。
- [ ] 所有历史图在决策态严格截止到扫描时点。
- [ ] 数据异常和缺失信息醒目标注。
- [ ] 相同币种跨 run 记录可以一处查看。
- [ ] 外链只作为核验快捷方式。
- [ ] Paper Trade 无方向/假设/失效条件时无法提交。
- [ ] 保存后自动进入下一候选，并可撤销上一步。
- [ ] 每次修改都有追加审计。
- [ ] 页面不存在真实下单入口。

## 10. 建议优先级

建议立即做 Phase A + Phase B 的最小闭环，暂缓前端框架重写和外部数据大接入。

第一版应优先解决三件事：

1. 把已有冻结数据变成完整决策卡。
2. 把“很多币的聊天清单”变成按优先级逐个处理的收件箱。
3. 把 Owner 决策直接写入受控服务和审计日志。

这三项完成后，当前研究系统才算拥有可长期使用的人机交互层；现有形态应被定义为“研究流程初版”，而不是最终产品。
